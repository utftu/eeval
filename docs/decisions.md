# Решения

Текущий набор решений, а не журнал. Решение изменилось — запись правится на месте, историю держит git.

## Стек

### Рантайм и форма пакета

Decided: Bun + TypeScript в strict, один пакет, исходники в `src/`. Родные API Bun предпочитаются встроенным модулям Node там, где они есть: `Bun.Glob` вместо своего обхода папок и своего списка расширений, `Bun.file().stat()` вместо `node:fs/promises`. `node:path` остаётся — своего у Bun нет.
Because: библиотека одна, делить нечего. Рантайм выбран, и городить поверх него слой совместимости не за чем; `Bun.Glob` заодно держит определение «что такое файл эвала» в одном паттерне, а не в паттерне плюс массиве суффиксов.
Not chosen: монорепа — по js-style берётся только когда иначе нельзя.

### Зависимости

Decided: `argblock` для разбора аргументов. Больше никаких — `logw` не подключается, пока не понадобится настоящее логирование (файл, уровни).
Because: свои пакеты — выбор по умолчанию перед популярными аналогами, но отчёт о прогоне это не лог, а продукт CLI, и печатается `console.log` — как и записано в js-style.
Not chosen: `logw` ради вывода — уровни, префиксы и провайдеры отчёту ничего не добавляют. commander, chalk — чужие и без причины.

У `--concurrency`, `--trials`, `--timeout` не задаётся `default`: в argblock параметр с дефолтом неотличим от отсутствующего.

### Воркеры и рантайм

Decided: воркеры на web-API — `new Worker(url)`, `self.onmessage`, `self.postMessage`, `terminate()`. Поддержка Node в задачи не входит: владелец не хочет на него завязываться.

Because: web-API — родной путь Bun, а не эмуляция чужого рантайма, и вся его нужная нам поверхность проверена замерами: убийство синхронно зависшего воркера, закрытие открытого `fetch` при `terminate()`, доставка abort во время `await fetch`, изоляция от `process.exit(1)` и необработанных исключений, `console.log` в общий stdout, спаун 2–4мс.

Not chosen: `node:worker_threads` — измерено, что один и тот же код работает и под Bun, и под Node 24 (Node сам снимает типы с `.ts`), но это его единственное преимущество, а Node не нужен. Взамен пришлось бы опереться на слой Node-совместимости Bun, который неполон ровно там, где API обещает больше: после `terminate()` Node присылает событие `exit` с кодом, Bun не присылает. Поверхность там же больше: `parentPort` типизирован как `MessagePort | null`, и каждый файл воркера начинается с проверки. Дочерние процессы (`Bun.spawn`, `child_process.fork`) — дают настоящую изоляцию памяти против OOM и падений нативных модулей, но кейсы это JS, ждущий сеть, а при `--concurrency 20` это двадцать рантаймов вместо двадцати потоков.

## Структура

Decided: у каждой сущности своя папка, даже если в ней только файл и тест: `discovery/`, `eval/`, `format/`, `pool/`, `runner/`, `storage/`. В корне `src/` остаются `eeval.ts` — вход пакета — и общие `consts.ts`, `types.ts`.
Типы лежат у своего хозяина:

- `eval/eval.ts` — API эвалов: `Eval`, `EvalCtx`, `Case`, `CaseProps`, `CaseResult`, `EvalEnt`, `CaseEnt`.
- `pool/protocol.ts` — то, что ходит между раннером, пулом и воркером: `Task`, `JobResponse`, `EvalConfig`.
- `types.ts` — только запись прогона: `TrialRecord`, `CaseRecord`, `EvalRecord`, `RunRecord`. Её собирает раннер, пишет `storage`, печатает `format`, одного хозяина у неё нет.

Because: владелец — в корне было слишком много файлов без папки, а в `types.ts` лежало всё подряд. Тип, у которого есть хозяин, лежит рядом с его кодом; общим остаётся только то, что делят три модуля.
Not chosen: папка только с трёх файлов на сущность — корень `src/` перерос десять файлов. Запись прогона в `runner/record.ts` — `storage` и `format` импортировали бы типы из раннера, хотя сам раннер им не нужен.

## Имена типов

Decided: тип называется по тому, откуда берётся значение.

| Откуда | Типы |
|---|---|
| пишет пользователь в файле эвала | `Eval` — функция `(ctx: EvalCtx) => void`; `EvalCtx`; `Case` — функция кейса; `CaseProps` — `name`, `minScore`, `timeout`; `CaseResult` |
| собирает `createEval` | `EvalEnt` — объект с маркером, именем и кейсами; `CaseEnt` — `CaseProps` плюс функция `Case`, его кладёт внутрь эвала `ctx.createCase` |
| присылает воркер родителю | `EvalConfig` — `EvalEnt` без функций: имя и `CaseProps[]`. Отдельного типа для кейса нет, это ровно `CaseProps` |
| раннер → пул → воркер | `Task` — запрос на исполнение, `list` или `run`; `JobResponse` — ответ на него |
| внутри пула | `Job` — исполнение одного `Task`: очередь, воркер, таймаут и тот, кто ждёт ответа |
| пишет раннер | `TrialRecord`, `CaseRecord`, `EvalRecord`, `RunRecord` — запись запуска, см. «Схема записи прогона» |

`{ kind: "abort" }` — не `Task`: в очередь не встаёт и своего ответа не имеет. Поэтому тип сообщения воркеру, `Task` или abort, описан на месте в `pool/worker.ts`.

Because: владелец — по имени должно быть видно, откуда что идёт. `JobResponse`, а не `WorkerResponse`: три ответа пул собирает сам, без воркера, — `PoolClosedError`, `TimeoutError`, `WorkerError`.
Not chosen: `ListedEval` и `ListedCase` — `Listed` читается странно. `EvalPlace` — обещает путь к файлу, а его в типе нет. `EvalData`, `EvalMeta`, `EvalInfo` — `Config` честнее: внутри имя и настройки кейсов. `CreatedEval`, `EvalInstance`, `CreateEvalResult` — у кейса не было бы пары, `createCase` ничего не возвращает. `CaseRun`, `CaseFn`, `CaseBody` — функция пользователя называется просто `Case`. `EvalProps` — `CaseProps` функция кейса не получает, а `EvalCtx` получает; одинаковый суффикс у разных по устройству вещей. `TaskRequest` рядом с `WorkerRequest` — было непонятно, чем они отличаются.

## API эвалов

### Форма описания eval

Decided: `createEval(name, fill)`, где `fill` — синхронная функция `Eval`, получающая `ctx`. Кейсы объявляются вызовами `ctx.createCase(props, run)`.

```ts
type CaseProps = {
  name: string;
  minScore: number;
  timeout?: number;
};

type CaseResult = {
  score: number;
  output?: unknown;
};

type Case = (signal: AbortSignal) => Promise<number | CaseResult>;

type EvalCtx = {
  createCase: (props: CaseProps, run: Case) => void;
};

type Eval = (ctx: EvalCtx) => void;

function createEval(name: string, fill: Eval): EvalEnt;
```

Имя эвала обязано быть непустым, других ограничений нет.

Кейс, которому сигнал не нужен, пишется без аргументов — функция без параметров подходит под этот тип, проверено `tsc --strict`.

Because: кейс остаётся обычным кодом — зовёт что хочет и как хочет, кейсы строятся циклом по датасету. Нет тройки `Input/Output/Expected`, которую декларативная форма тянет дженериками через каждый скорер.
Not chosen: декларативная `createEval({name, cases, task, scorers})` — один общий `task` на все кейсы, три уровня дженериков, скорер становится сущностью публичного API. Совместимость со скорерами autoevals держала эту форму и перестала иметь значение, как только скорер перестал быть нашим типом.

### Балл кейса

Decided: одно число 0..100 — измеренная правильность ответа ИИ. Уверенность сервиса баллом сама по себе не является, она может входить в него слагаемым по решению автора кейса.
Because: владелец — правильность должна измеряться одним числом.
Балл проверяется на границе воркера: не число, не конечное число или выход за 0..100 роняют кейс ошибкой. Кейс, вернувший что-то кроме числа или объекта со `score`, — тоже.

Not chosen: `Record<string, number>` для нескольких метрик из одного вызова — один порог не натягивается на бинарный вердикт и непрерывную уверенность разом; несколько метрик означают несколько кейсов. Шкала 0..1 — была нужна только ради autoevals.

### Порог кейса

Decided: `minScore` обязателен в `CaseProps`. Кейс, который хочется измерять, но не хочется делать причиной красного прогона, пишет `minScore: 0`.
Because: владелец — кейс по сути тест, он обязан валидировать. Отсюда же код возврата процесса, красный/зелёный в выводе и смысл прогона в CI.
Not chosen: «порога нет — значит только измеряем» — правило хуже, чем ноль в поле. Дефолт на уровне eval — два места, где живёт одно число, и правило приоритета между ними.

Имя поля `minScore` — рекомендация модели, владелец его не подтверждал; в его наброске стояло `score`. Переименовано быть может.

### Имя кейса

Decided: обязательно, лежит в `CaseProps`, уникально в пределах файла — на дубликате `createCase` бросает. Имя — ключ истории: переименовал кейс, получил новый кейс с пустой историей.
Because: строки в `history.jsonl` нечем сопоставить между прогонами, а вся ценность истории в том, что кейс вчера давал 92, а сегодня 40. Уникальность из пожелания стала правилом, когда кейс начал адресоваться по имени через границу процесса.
Not chosen: нумерация по порядку — вставка кейса в середину переименовывает всё, что после неё.

### Возврат кейса

Decided: `number | { score, output? }`. `output` — `unknown`, едет через structured clone и попадает только в `latest.json`, как есть; библиотека внутрь не смотрит и ничего оттуда не считает. Кладётся в него то, что нельзя восстановить, открыв файл эвала: ответ сервиса, а не вход. Не клонируемое содержимое (функция, экземпляр класса) роняет кейс ошибкой клонирования, а не теряется молча.
Because: аналогия с тестом ломается на воспроизводимости — `bun:test` перезапускается и даёт то же самое, ИИ даёт другое. Без этого поля кейс, который бросил исключение, диагностируем по тексту ошибки, а кейс, который ответил неправильно, хранит `score: 0` и больше ничего: редкая поломка разбирается, частая нет.
Not chosen: `caseCtx.note(value)` — второй ctx-объект, который надо объяснять, ради того же самого. Только `number` — теряется единственный след упавшего ответа.

### Свёртка правильности

Decided: правило свёртки живёт в теле кейса, библиотека о нём не знает. Проверки переиспользуются как обычные функции.
Because: спор «уверенно неправильный ответ хуже неуверенно неправильного?» решается строкой, которую видно при чтении файла эвала. eeval умеет ровно три вещи: запустить, сравнить с порогом, записать.
Not chosen: скорер как сущность API (`createScorer`) — под-грамматика, которую надо описывать, версионировать и объяснять, вместо вызова функции.

## Запуск

### CLI

Decided: `run` — команда по умолчанию, голый `eeval` запускает прогон. Позиционные аргументы — пути. Файлы эвалов: `*.eval.ts`, а также `.js` и `.tsx`.
Because: запуск — то, ради чего инструмент зовут, он не должен требовать слова.
Not chosen: обязательная подкоманда.

### Discovery

Decided: воркер делает `import(file)` и перебирает экспорты модуля, узнавая эвал по полю-маркеру на самом значении. Эвал должен быть доступен через экспорты; **имя экспорта значения не имеет**.

```ts
const INSTANCE_KEY = "__eeval";
const INSTANCE_VALUE = "eval";

function checkEval(mayEval: unknown): mayEval is EvalEnt {
  if (
    mayEval &&
    typeof mayEval === "object" &&
    INSTANCE_KEY in mayEval &&
    (mayEval as Record<string, unknown>)[INSTANCE_KEY] === INSTANCE_VALUE
  ) {
    return true;
  }

  return false;
}
```

Правила: файл, в экспортах которого нет ни одного эвала, — ошибка, а не тихий пропуск; несколько эвалов в одном файле можно; имя эвала уникально в пределах прогона, коллизия — ошибка; поиск файлов идёт по `*.eval.ts`, `.tsx`, `.js` от позиционных путей, а без них от cwd вглубь, минуя `node_modules` и папки на точку.

Because: измерено, что регистрация побочным эффектом ломается при двух копиях пакета в дереве — файл эвала импортировал одну копию, код воркера другую, реестр второй копии оказался пуст, и эвалы потерялись бы молча: файлы нашлись, кейсов ноль, ошибки нет. Две копии — обычное дело (линк, монорепа, невышедший dedupe). Маркер этого не касается, потому что читаются экспорты самого модуля, а не наше глобальное состояние. Ошибка на файле без эвалов ловит вторую половину: `createEval(...)` без экспорта невидим, и молчаливый пропуск превратил бы опечатку в пустой прогон.

Not chosen: регистрация побочным эффектом, как у Braintrust и Evalite, — измерено, ломается. Суффикс имени экспорта (`*Eval`) — переименование переменной ломало бы прогон, а `export const fakeEval = { name, cases }` проходил бы проверку и падал уже внутри раннера; проверка должна спрашивать значение, а не догадываться по имени. Разбор исходников вместо `import()` — дороже и хрупче.

Порядок эвалов внутри файла — алфавитный по имени экспорта, потому что `for...in` по модулю отдаёт их отсортированными, а не в порядке объявления. Порядок по исходнику потребовал бы его читать; не делаем.

### Модель выполнения

Decided: пул из N воркеров поднимается на старте прогона, кейсы раздаются по мере освобождения, по одному кейсу в воркере за раз. Новый воркер поднимается только взамен убитого. `--concurrency N` — это и есть число воркеров. Родитель не исполняет пользовательский код вообще: перечисление кейсов тоже делает воркер.

Because: измерено, что ни bun:test, ни vitest зависший тест не прерывают — оба вешают ярлык таймаута задним числом (синхронный цикл на 4с при `--timeout 300` отработал все 4с в обоих), а на настоящем `while(true)` оба висят навсегда. Им это можно: брошенный юнит-тест ничего не стоит. Брошенный кейс эвала держит открытое соединение с платным API и тянет токены, за которые платят; при `--concurrency 20` раннер бросает двадцать запросов и тут же запускает следующие двадцать, упирается в rate limit, и упираются в него следующие кейсы — в истории это выглядит как падение качества модели. Проверено, что `terminate()` закрывает открытый `fetch` (сервер видит закрытие соединения сразу), убивает синхронно зависший воркер, и что `process.exit(1)` или необработанное исключение в воркере не роняют родителя.

Not chosen: один процесс с `Promise.race` — синхронное зависание не ловится вовсе, потому что таймер не получает очереди; отмена работает только если пользователь протащил `AbortSignal` до своего `fetch`. Изоляция по файлу, как в vitest, — один зависший кейс уносит все оставшиеся кейсы своего файла. Воркер на кейс — спаун стоит 2–4мс и сам по себе дёшев, но платить пришлось бы за `import` файла эвала со всем его графом, а это цена пользовательская и неизвестная. Много кейсов в одном воркере — убийство зависшего утащило бы соседей.

Скоростью это не покупается: нагрузка упирается в ожидание сети, один асинхронный цикл её и так насыщает.

Trials одного кейса уходят в пул одновременно, а не по очереди. Нагрузку это не увеличивает — её ограничивает число воркеров, — зато простаивающие воркеры заняты. Порядок trials в записи — порядок запуска, а не завершения. Плата принята владельцем: кейс идёт одновременно сам с собой, и сервис с состоянием (создаёт заявку, пишет в одну тестовую учётку) может ронять trials, которые по очереди прошли бы.

Следствия, с которыми живём: код верхнего уровня файла эвала выполняется по разу на воркер и ещё раз после каждого респауна; состояние модуля живёт между кейсами внутри одного воркера и не живёт между воркерами; закладываться на это нельзя. Кейс не может прибраться при жёстком убийстве — `finally` не отработает. Честный потолок `--concurrency` — несколько десятков; 200-кратная параллельность это память, которую не хочется платить.

### Таймаут

Decided: `--timeout` задан в CLI — он побеждает везде, включая кейсы со своим значением. Не задан — каждый кейс берёт свой `timeout` из `CaseProps`. Кейс своего не имеет — константа 60с. Милисекунды. Отсчитывается на попытку, не на кейс целиком.

Порядок при истечении: родитель шлёт воркеру `abort`, тот роняет свой `AbortController`; у кейса падает `fetch`, отрабатывает его `finally`, воркер сам отчитывается ошибкой и остаётся жив. Если через секунду воркер молчит — `terminate()` и респаун. Секунда отсрочки — константа в коде.

Таймаут это исключение, а не балл 0, поэтому попадает под `--retries`.

Because: `timeout` в кейсе и `--timeout` в CLI — разные высказывания. Первое говорит «этому кейсу столько нужно по-честному», это свойство кода. Второе — «сейчас, в этом окружении, ничего не смеет идти дольше», распоряжение того, кто запускает. Распоряжение, которое набрали руками, бьёт значение, записанное в файле давно. Мягкий шаг ловит зависшую сеть и даёт кейсу прибраться, жёсткий ловит зависший код; они не пересекаются — воркер в синхронном цикле сообщение об abort не получит, очередь не крутится. Проверено, что сообщение обрабатывается прямо во время `await fetch` и отмена срабатывает в срок. Балл 0 за таймаут означал бы, что медленная сеть ухудшает модель в отчёте.

Последствие принято осознанно: кейс, которому честно нужно 120с, под `--timeout 30000` упадёт. В этом и смысл распоряжения.

Not chosen: «кейс перебивает флаг» — было записано первым и развёрнуто владельцем: тогда глобальным флагом нельзя ограничить прогон, а это главное, ради чего его набирают. Только глобальный `--timeout` без значения в кейсе — его приходится ставить по самому медленному кейсу, после чего для быстрых он ничего не ловит, а одно число не обслуживает разом классификатор на 2с и агентский цикл на 120с. Только `terminate()` без abort — кейс не может прибраться, и каждый таймаут стоит респауна с повторным импортом. Только abort без убийства — не ловит синхронное зависание. Флаг для секунды отсрочки — число, которое никто не крутит.

### Повторы

Decided: два независимых параметра, оба в CLI, оба живут в родителе.

- `--retries` — ремонт. Кейс бросил исключение (429, таймаут, обрыв) — задание отправляется заново. Балл ниже порога повтора не вызывает.
- `--trials` — измерение. Кейс запускается N раз всегда, каждый trial сравнивается с порогом отдельно.

Складываются вложенно: trials снаружи, retries внутри. `--trials 5 --retries 2` — пять измерений, каждое до трёх попыток.

Because: ремонт не меняет измеряемое число, он его добывает; в trials повтор и есть число.
Not chosen: один общий параметр — исключение засчиталось бы trial с плохим результатом, и rate limit опускал бы оценку качества модели. Повтор на балле ниже порога — балл превращается из качества в «лучший из N попыток» и прячет плохие trials, ради которых они и существуют. `retries` в `CaseProps` — флейковость это свойство окружения, а не кейса, и два места означают правило приоритета.

### Прохождение кейса

Decided: кейс прошёл, если в каждом trial балл не ниже `minScore`. Trial, упавший с ошибкой после исчерпания `--retries`, кейс валит. Баллы trials ничем не сворачиваются: своего балла у кейса нет, в запись идут trials и `passed`.

Because: владелец — ничего не сворачиваем и суммарный результат trials не пишем. Каждый trial — самостоятельный замер, и провальный trial виден красным кейсом, а не растворяется в числе.

Порог сравнивается как «не ниже», а не «строго больше»: иначе кейс с `minScore: 0`, который только измеряет, падал бы на балле 0.

Not chosen: среднее, сравниваемое с `minScore`, — было записано первым и снято владельцем: 100/100/10 проходило порог 70 при провальном trial. Доля успешных trials параметром — второй порог рядом с первым.

### Протокол воркера

Decided:

```ts
type EvalConfig = { name: string; cases: CaseProps[] };

type Task =
  | { kind: "list"; file: string }
  | { kind: "run"; file: string; evalName: string; caseName: string };

type JobResponse =
  | { kind: "cases"; evals: EvalConfig[] }
  | { kind: "result"; score: number; output?: unknown }
  | { kind: "error"; name: string; message: string; stack?: string };
```

`evalName` в задании и группировка кейсов по эвалам в ответе — поправка к первой редакции протокола, найденная при реализации: имена кейсов уникальны внутри эвала, а в одном файле эвалов может быть несколько, поэтому пары файл-кейс не хватает для адресации.

Because: замыкание через границу процесса не переезжает, поэтому задание адресует кейс парой файл-имя, а воркер импортирует файл сам. Ошибка разбирается на поля вручную, а не едет объектом `Error`: проверено, что structured clone схлопывает подкласс в обычный `Error` (`constructor.name` становится `Error`) и теряет собственные поля — `message` и `stack` выживают, добавленный `code = 42` приходит как `undefined`.
Not chosen: слать в воркер сам кейс — функции не сериализуются. Перечислять кейсы в родителе — родитель начал бы исполнять пользовательский код.

### Вывод

Decided: раннер не печатает ничего. Готовый кейс уходит в колбэк `reportCase(evalName, record)`, записи прогонов возвращаются наружу; печатает CLI обычным `console.log`. Строки собирают чистые `formatCaseLine` и `formatSummary`. Прогон красный, если красный хоть один кейс, и это же код возврата процесса.

```
return-decision
  ok    брак с фото в срок       94/91/91      2.5s
  fail  брак без фото            71/err       62.1s  TimeoutError: не уложился
  всего 2, прошло 1, упало 1, 64.6s
```

Because: отчёт о прогоне — продукт CLI, а не лог; уровни, префиксы и провайдеры ему ничего не добавляют. Решение отделено от действия: раннер считает, CLI печатает, и обе форматирующие функции тестируются без воркеров и без вывода. Печатается балл каждого trial, потому что кейс гейтит каждый из них.
Not chosen: `logw` — снят владельцем, вернётся, если появится настоящее логирование. Свой тип `Reporter` — дублировал бы `Provider` из logw и не нужен, пока печатает CLI. Флаг `--json`.

Точные символы и выравнивание — Level 3, меняются без спроса.

## Хранение

### Корень и файлы

Decided: корень `.eeval` в cwd, без папок на эвал.

- `.eeval/history.jsonl` — одна строка на запуск: `RunRecord` со всеми эвалами запуска, без `output`. Дописывается в конце запуска. Упавший кейс сохраняется с записью об ошибке.
- `.eeval/latest.json` — три последних `RunRecord` целиком, новый сверху, вместе с `output`. `JSON.stringify(x, null, 2)`.

`.gitignore` инструмент не трогает.
Because: владелец — всё лежит в двух файлах в корне, и запуск — одна единица: одна строка истории, общие `options`. История одного эвала достаётся из `evals` по `name`. Имя эвала больше не становится именем папки, поэтому других ограничений на него, кроме непустоты, нет. `jsonl` дописывается без чтения файла целиком, `latest.json` читается глазами.

Плата принята: запуск одного эвала через путь вытесняет из `latest.json` последние результаты остальных. Два процесса eeval одновременно в одной cwd перезаписывают `latest.json` друг поверх друга; `history.jsonl` дописывается короткими порциями, но без гарантии.

Not chosen: папка на эвал, `.eeval/<eval-name>/` — было записано первым и снято владельцем. Строка истории на прогон одного эвала — запуск терялся, а `options` повторялись в каждой строке. `latest.json` как три последних прогона каждого эвала, объектом по имени, — не вытеснял бы чужие результаты, но владелец выбрал запуск целиком.

### Схема записи прогона

Decided: одна схема, из которой в историю не идёт одно поле. Строка `history.jsonl` — запись запуска без `output`. Элемент `latest.json` — та же запись вместе с `output`.

```json
{
  "version": 1,
  "startedAt": "2026-09-12T13:40:11.204Z",
  "ms": 48210,
  "options": { "trials": 3, "retries": 2, "timeout": 60000 },
  "evals": [
    {
      "name": "return-decision",
      "ms": 47900,
      "total": 2,
      "passed": 1,
      "cases": [
        {
          "name": "брак с фото в срок",
          "minScore": 80,
          "passed": true,
          "trials": [
            { "score": 94, "ms": 1820, "retries": 0 },
            { "score": 91, "ms": 1902, "retries": 1 },
            { "score": 91, "ms": 1755, "retries": 0, "output": { "verdict": "refund", "score": 91 } }
          ]
        },
        {
          "name": "брак без фото",
          "minScore": 60,
          "passed": false,
          "trials": [
            { "score": 71, "ms": 2100, "retries": 0 },
            { "error": { "name": "AbortError", "message": "таймаут 60000мс" }, "ms": 60001, "retries": 2 }
          ]
        }
      ]
    }
  ]
}
```

```ts
type RunRecord = {
  version: number;
  startedAt: string;
  ms: number;
  options: { trials: number; retries: number; timeout?: number };
  evals: EvalRecord[];
};

type EvalRecord = {
  name: string;
  ms: number;
  total: number;
  passed: number;
  cases: CaseRecord[];
};
```

Запуск красный, если красный хоть один кейс; отсюда код возврата процесса.

Because: своего `score` у кейса нет — баллы trials не сворачиваются, см. «Прохождение кейса». `options` пишутся, потому что прогон с `--trials 5` и с `--trials 1` дают несравнимые числа, и без этого поля история врёт молча. `minScore` дублируется в кейсе, хотя он есть и в файле эвала: порог меняют, и надо знать, с какой планкой сравнивали тогда. `options` и `version` пишутся на весь запуск, а не на эвал: у всех эвалов запуска они общие. `startedAt` у эвала нет — эвалы идут друг за другом, хватает `ms`. Счётчиков на весь запуск нет, они считаются из `evals`. `version` — формат переживёт не одну правку, а строки в `jsonl` остаются от старых версий навсегда. `retries` названы как флаг, чтобы `--retries 2` и `retries: 2` читались одним словом; подробности успешно отретраенных падений не хранятся, это диагностика сети, а не модели.

`output` держится только в `latest.json` — решение владельца: место экономится, а для ретроспективы ответ модели не важен. Плата: ответ живёт три запуска, дальше остаются только числа.

Not chosen: `output` в обоих файлах — `history.jsonl` рос бы блобами без ротации, двести кейсов на пять trials с ответом в пару килобайт дают мегабайты в одной строке. Две разные схемы для двух файлов — два формата пришлось бы синхронизировать руками. Эффективный `timeout` кейса в записи — на число не влияет.

## Не подтверждено владельцем

Реализовано так, как предлагалось, но словом не закрыто — вето принимается.

- `evalName` в задании воркера и группировка кейсов по эвалам в ответе. Поправка к первой редакции протокола: пары файл-кейс не хватает для адресации, потому что имена кейсов уникальны внутри эвала, а эвалов в файле может быть несколько.
- Форма вывода целиком: `reportCase` вместо логгера, вид строки кейса и итога.

## Не решено

- Раннер обходит эвалы по очереди, поэтому параллельность упирается не в `--concurrency`, а в число кейсов текущего эвала. Лечится плоским списком задач на все эвалы разом, но тогда строки разных эвалов в выводе перемешаются.
